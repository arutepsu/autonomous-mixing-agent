# ADR-016 — application observation and decision contracts (2026-10-20)
- Status: Proposed; awaiting owner review of the implementing task (Task 3A).
- Decision: add an application layer `autonomous_mixing.application` that owns port interfaces and their request/response records.
  1. Dependency direction: application depends only on the standard library, `autonomous_mixing.domain` and its own modules. It never imports infrastructure, presentation, the existing M0 audio modules, provider SDKs or storage libraries, and the domain never imports application. Tests enforce both, including resolved relative imports and look-alike package names.
  2. Expected port failures are typed values, not exceptions: `PortResult = Success[T] | PortFailure`. `PortFailure(code: PortFailureCode, message: str, retryable: bool)` holds no exception instance, credential, raw response or provider object. `retryable` is advisory and triggers no retry. Unexpected exceptions remain possible.
  3. Ports are plain `typing.Protocol` classes (not runtime-checkable): `AudioAnalyzer.analyze(AnalysisRequest) -> PortResult[AnalysisResponse]` and `DecisionController.decide(DecisionRequest) -> PortResult[DecisionResponse]`.
  4. Requests carry source artifacts as an `ArtifactCheckpoint`, the membership of the observed project state, which must match the snapshot. Member artifacts keep their production revisions (ADR-011, ADR-015). `AnalysisRequest(snapshot, checkpoint, scope, specification)` also validates the scope against the snapshot; members need not each cover the whole scope. `DecisionRequest(snapshot, context, controller, observations, checkpoint, usage, limits)` validates context and every observation's sources. Usage beyond limits stays representable. (Amended 2026-10-21 by [ADR-019](0019-fixed-input-gain-and-composite-project-state.md): both requests carry one composite `state: ProjectState` instead of separate snapshot and checkpoint fields; checks use `state.snapshot` and `state.audio` unchanged.)
  5. `validate_analysis_response` checks each observation's sources via `validate_observation_sources`, the requested analysis spec and metric set, scope containment (tracks, time, an explicit contained band when the request restricts frequency), at least one observation per requested metric, and no two observations of the same metric and scope. `validate_decision_response` runs `validate_decision_references` against the request and requires the decision's controller identity to equal the requested one.
- Source: owner's Task 3A instruction of 2026-10-20, amended by the owner's choice on 2026-10-20 to carry a checkpoint instead of an artifact tuple (see Deviation).
- Deviation from the instruction as first written: it specified `artifacts: tuple[AudioArtifact, ...]` in both requests and required every artifact's revision to equal the snapshot revision. That reintroduced the production-revision rule removed in the provenance correction, and `validate_observation_sources` now needs a checkpoint. The owner chose to replace the field with `checkpoint: ArtifactCheckpoint`.
- Rationale: typed failures and Protocol ports keep analysis and decision providers interchangeable and the application testable offline without provider SDKs (QR-02, QR-07). Checkpoint-based requests keep observation provenance consistent with exact artifact-reference rollback (FR-10, FR-12). Structural completeness checks support recorded measurements and decisions (FR-03, FR-04, FR-06) without judging numeric or perceptual validity.
- Consequences:
  - Groundwork only for FR-03, FR-04, FR-06, FR-12, QR-02, QR-07 and SR-10; none is met. No analyzer, controller, adapter, orchestration, retry, budget enforcement, persistence or CLI integration exists.
  - The decision request is not the complete future controller input. Problem candidates (FR-05, D11), action capabilities and permitted actions (D5), attempt history, raw provider responses and prompt/version records (QR-03) are deferred contracts.
  - The request carries no hidden evaluation data (SR-10), but artifact locations are ordinary runtime references; sandboxing a future provider is not provided by these records.
  - The scope-containment rules duplicate those in `RunConfiguration.validate_against` (ADR-014); a later task may share them once both callers are stable.
