# ADR-017 — domain organized into component packages with enforced dependencies (2026-10-20)
- Status: Proposed; awaiting owner review of the refactor.
- Decision: organize `autonomous_mixing.domain` into eight component packages, each with an explicit `__init__.py` public interface (`__all__`), and enforce an acyclic dependency matrix. This is a structural refactor: no field, enum value, validation rule, exception category, default, signature, identity or provenance meaning changes.
  1. Components and ownership: `shared` (typed identifiers, `Revision`, `VersionRef`, the `require_*` invariant helpers), `project` (tracks, snapshot, artifacts, `ArtifactCheckpoint`, scope), `context`, `observation` (records, specifications, provenance check), `action` (operations, proposals, execution receipts, `derive_candidate_checkpoint`, rollback), `decision`, `validation` (criteria, results, consistency check) and `run` (configuration, budgets, run records, correction attempts, attempt reference check). Project owns checkpoint membership; action owns deriving candidate membership from a receipt, so project stays independent of action.
  2. Allowed sibling dependencies: shared → none; project → shared; context, observation, action → shared, project; decision → shared, project, context, observation, action; validation → shared, project, observation; run → all others. No component imports run. The domain never imports application, infrastructure, M0 audio, presentation or third-party packages.
  3. Cross-component and application imports target component interfaces (`from autonomous_mixing.domain.project import ArtifactCheckpoint`), never another component's internal files. Imports within a component may target its own files.
  4. Compatibility: the root `autonomous_mixing.domain` (all 76 previous exports) and the legacy modules `values` and `execution` remain as thin re-exports of the same objects, with no definitions of their own. They are the only places allowed to import across components outside the matrix. New code and normal tests do not use them; only compatibility tests do. Removing them needs a later explicit task. Module-qualified class paths changed; pickle compatibility is not claimed.
  5. Enforcement is test-only (`tests/unit/test_domain_component_boundaries.py`). The import checker resolves absolute, relative and from-package imports against the real source tree, matches exact package segments, treats unresolved imports as violations, checks the matrix, public-interface access and compatibility exceptions, and detects cycles. `tests/unit/test_domain_component_compatibility.py` checks object identity of legacy, root and component imports and the signatures of the seven cross-record and derivation functions.
- Source: owner-approved domain component refactor design and migration plan (2026-10-20), kept in the owner's planning workspace.
- Rationale: the flat modules mixed responsibilities (for example, checkpoints lived with execution receipts, and observation depended on execution only for checkpoints). Cohesive components with explicit interfaces and an enforced, acyclic dependency direction make the domain easier to understand and keep later application work from coupling to internals (QR-07 maintainability, ADR-006 traceability).
- Consequences:
  - ADR-011 to ADR-016 keep their meaning. Their module names now refer to component packages, and ADR-015's `domain.execution` objects live in `domain.project` (`ArtifactCheckpoint`) and `domain.action` (receipts, rollback, derivation).
  - Small validation helpers are kept locally at their owner rather than shared (e.g. the unique-artifact check exists in `project.checkpoint` and `action.execution`).
  - Unchanged and still deferred: problem candidates, execution semantics of absolute gain, a metric/unit catalog, complete project-state ownership, run events, persistence, evaluators and application enforcement.
