# ADR-015 — correction-attempt and artifact-checkpoint records (2026-10-19)
- Status: Proposed; awaiting owner review of the implementing task (Task 2D).
- Decision: extend the dependency-free domain layer (ADR-011 to ADR-014) with `domain.execution` and a `CorrectionAttempt` record in `domain.run`.
  1. Offline rollback works on artifact references. Processing writes separate candidate artifacts. Acceptance changes which artifacts are designated as accepted, and rollback restores the previous accepted references. No approximate inverse transformation is applied.
  2. Provenance and state membership are separate. `AudioArtifact.revision` is the production revision and is never retagged. `ArtifactCheckpoint` (`CheckpointId`, project, revision, a non-empty tuple of `AudioArtifact`) records the artifact membership of one project state; its `revision` identifies that state. Members must share its project and have unique IDs, but may have different production revisions (unchanged artifacts are retained from earlier states). A checkpoint may describe a candidate or an accepted state; its existence alone does not establish acceptance. Stems, groups and mixes may be mixed; complete track coverage is not required. An initial checkpoint matches the initial snapshot through `ArtifactCheckpoint.validate_against(snapshot)` (project, state revision, known tracks); previously produced artifacts may be reused.
  3. `ExecutionReceipt` records one execution with `ExecutionStatus` NOT_STARTED, FAILED, CANDIDATE_READY or UNCERTAIN. CANDIDATE_READY requires a new candidate revision, non-empty newly produced candidate artifacts, non-empty explicit `superseded_artifact_ids` (for the supported track-gain operation) disjoint from the candidates, and no `ExecutionIssue`. FAILED and UNCERTAIN require an issue. Only CANDIDATE_READY may claim a candidate revision, artifacts or superseded IDs. No status authorizes acceptance or another edit, and FAILED does not claim cleanup. Replacement is never inferred: future execution planning must explicitly supersede every affected derived artifact (e.g. groups and mixes containing an edited track). Dependency invalidation is not implemented here.
  4. `RollbackReceipt` (`RollbackStatus` VERIFIED, FAILED or UNCERTAIN) names the execution, the checkpoint and the restored artifact IDs. Only VERIFIED claims restored IDs. `validate_rollback_references` requires the VERIFIED set to equal the checkpoint's artifact IDs exactly.
  5. `CorrectionAttempt` links attempt, run, decision and action IDs with the before checkpoint, optional execution, validation and rollback evidence, and an `AttemptDisposition`:
     - PENDING: partial records, not permission to execute.
     - ACCEPTED: CANDIDATE_READY execution, ACCEPTED validation verdict, no rollback.
     - ROLLED_BACK: a VERIFIED rollback matching the execution and checkpoint.
     - FAILED: NOT_STARTED or FAILED execution and no rollback.
     - UNRESOLVED: uncertain execution, or failed/uncertain rollback.
     Construction also requires the receipt to agree with the attempt action and to pass `validate_receipt_against_checkpoint` against the before checkpoint (item 7). Embedded validation requires a CANDIDATE_READY execution and an ATTEMPT-mode assessment, whatever the disposition: an INITIAL assessment describes the starting state and is never evidence for a correction attempt, though it remains valid on its own. Any rollback needs a matching execution.
  6. `validate_attempt_references(attempt, run, decision)` checks:
     - run ID, decision ID and action ID agreement, and a ProposeAction outcome;
     - project agreement across run, checkpoint and decision;
     - decision expected revision equal to the checkpoint revision, which may differ from `run.initial_revision` after earlier accepted attempts;
     - context ID/version and controller against the run configuration;
     - checkpoint tracks within the run scope;
     - validation against the run criteria via `validate_validation_references`.
  7. `validate_receipt_against_checkpoint(receipt, before)` requires matching project and before revision, superseded IDs that are members of the before state, and candidate IDs disjoint from every before-state ID (no ID reuse). `derive_candidate_checkpoint(previous, receipt, checkpoint_id)` requires CANDIDATE_READY and builds the candidate state at the candidate revision: the previous artifacts minus the superseded ones, unchanged and in previous order, followed by the candidates in receipt order. It constructs candidate membership only and does not accept the correction. (Items 2, 3 and 7 amended 2026-10-20 before acceptance: the earlier rule that every checkpoint artifact shares the checkpoint revision contradicted retaining unchanged artifacts.)
- Source: owner's Task 2D instruction of 2026-10-19; mixing-core design section 4 (Action, Run); FR-10 exact restoration.
- Rationale: FR-10 requires that reverting restores the previously accepted result exactly. With immutable source and output artifacts (QR-01), exact restoration is a change of accepted references, which can be recorded and checked. An attempt record that links decision, execution, validation and rollback evidence supports complete run records (FR-12, QR-03), and explicit UNRESOLVED/UNCERTAIN states keep unknown outcomes from being reported as success or failure.
- Consequences:
  - Groundwork only for FR-08 to FR-12, QR-01 and QR-03; none is met. Matching IDs are not proof of exact audio restoration: a future adapter must verify artifact integrity (hashes) and the current accepted-reference state before issuing VERIFIED. Forbidding candidate-ID reuse keeps ID-based rollback checks meaningful.
  - Item 1's accepted state after an accepted attempt is the derived candidate checkpoint; designating it as accepted is application work.
  - Not modelled: file I/O, hashing, processing, cleanup of FAILED candidates, persistence, execution services, run events, lifecycle transitions and the coordinator. Run membership of attempts (e.g. a `Run.attempts` collection) is not recorded on `Run`. Candidate-artifact tracks are not checked against the run scope.
  - Whether a ROLLED_BACK attempt may follow an ACCEPTED validation verdict (e.g. restoration after a later persistence failure) is not restricted here; the coordinator task must decide.
