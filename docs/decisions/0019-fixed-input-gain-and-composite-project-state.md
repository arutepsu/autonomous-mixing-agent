# ADR-019 — fixed-input gain semantics and composite project state (2026-10-21)
- Status: Proposed; awaiting owner review of the implementing migration.
- Decision: define what `SetTrackGain` means for future execution, and represent gain settings and rendered-audio membership together in one immutable project state. This deliberately changes several constructor and function contracts; it is not a structural refactor.
  1. Gain semantics: `gain_db` is absolute additional gain relative to an explicitly fixed runtime input artifact of the track. It is never a delta applied to the latest output. Setting -3 dB twice means -3 dB in total, and -6 dB after -3 dB means -6 dB in total. 0 dB means the fixed input level, including any effects already baked into it. A missing gain state never means 0 dB. Initializing a new run from an earlier accepted state must explicitly retain its inputs and settings or explicitly start a new baseline. Runtime inputs may contain an injected research defect; they are not hidden clean/reference audio (ADR-010).
  2. New records in `domain.project`:
     - `TrackGainState(track_id, input_artifact, gain_db)`: the input must be a STEM whose source tracks are exactly `(track_id,)`; the gain is a finite float-representable number with no default or bounds.
     - `ProjectProcessingState(project_id, revision, track_gains)`: unique tracks; inputs belong to the project; one artifact ID never carries conflicting metadata. Coverage may be partial or empty, and absence means unrepresented, not unity gain. `validate_against(snapshot)` checks project, state revision and known tracks.
     - `ProjectState(snapshot, processing, audio)`: all three share the project and state revision; `project_id` and `revision` are derived properties. A fixed input need not be a current audio member, because a superseded baseline must stay available to later execution, but where its ID is a member, metadata must match exactly. A state may describe a candidate or an accepted state; constructing it accepts nothing and does not prove rendered files reflect the settings.
  3. `domain.action.derive_candidate_project_state(previous, receipt, action, checkpoint_id, captured_at)` purely assembles the candidate state claimed by a CANDIDATE_READY receipt and its action:
     - the action ID, project and expected revision must agree, and the target needs an explicit gain state;
     - the snapshot keeps the complete track inventory and order at the candidate revision and the supplied UTC time;
     - audio comes from `derive_candidate_checkpoint`;
     - only the target's gain is replaced, and inputs, non-target settings and order are unchanged.
     It never renders, accepts, computes deltas, infers baselines or discovers dependent artifacts. (Clarified 2026-10-21, audit F1/F5: it first runs `validate_gain_execution(previous, receipt, action)`. That check requires matching identities, an explicit target gain state and a current STEM of exactly the target. It also requires the receipt to supersede every current artifact whose sources include the target and nothing else, replaced one-for-one by kind and contributor set, with multiplicity kept. Derivation also rejects a candidate revision in `ProjectState.known_revisions`: the state revision and the production revisions of audio members and fixed baselines. Generic `derive_candidate_checkpoint` checks only the revisions visible in its membership. These are local collision and metadata-consistency checks, not proof of rendering, global uniqueness or group processing support.)
  4. Intentional contract changes:
     - `CorrectionAttempt.before_checkpoint` → `before_state: ProjectState`, and a new `candidate_state: ProjectState | None`, required exactly when execution is CANDIDATE_READY, whatever the disposition, including PENDING. Construction checks the candidate's project, receipt candidate revision, identical track inventory and order, exact expected audio membership, and unchanged represented tracks and fixed inputs. `validate_attempt_references` (signature unchanged) additionally requires an explicit target gain state, the target gain equal to the decision's requested value, and every non-target setting and fixed input unchanged; it uses the before state rather than `run.initial_revision`.
     - `RollbackReceipt.restored_artifact_ids` → `restored_state: ProjectState | None`, required for VERIFIED and forbidden for FAILED/UNCERTAIN. `validate_rollback_references(receipt, before_state)` checks the checkpoint identity against `before_state.audio`, and for VERIFIED requires exact equality with the saved before state. That covers settings, audio and snapshot (including the original capture timestamp), so restoring audio only or settings only cannot be verified.
     - `AnalysisRequest(state, scope, specification)` and `DecisionRequest(state, context, controller, observations, usage, limits)` replace separate snapshot and checkpoint fields; validators and admission read `state.snapshot` and `state.audio`. Admission decisions, rejection codes and order, bounds, reference semantics and provenance checks are unchanged.
     - Old constructor shapes are not emulated, and no production default baseline or processing state is supplied. Other public objects keep their identity; root exports grow from 76 to 80.
- Source: owner-approved processing-state specification and migration plan (2026-10-20/21), with the owner's confirmations of 2026-10-21: rollback selects the saved state including its timestamp; constructors check embedded consistency while reference validation checks the action-specific gain change; CANDIDATE_READY requires a candidate state even when PENDING; the complete track inventory and order are preserved.
- Rationale: without a fixed input, "set gain to -3 dB" is ambiguous, and repeated processing of the latest output would accumulate changes. Pairing settings with audio in one state makes candidate derivation, acceptance and exact rollback (FR-10) refer to the same complete state, and prevents callers from combining a snapshot and audio from different states (FR-12, QR-01).
- Consequences:
  - Groundwork only for FR-08 to FR-12 and QR-01; none is met. No DSP formula, rendering, hashing, file access, persistence, execution service or coordinator exists. Structural consistency and equal metadata are recorded claims, not proof of output fidelity; a future executor must verify outputs and update every affected mix or group, and a future adapter must verify files and the accepted-reference state before issuing VERIFIED.
  - Retained baselines must stay available for later execution; retention and cleanup that protects these input dependencies are future adapter responsibilities.
  - Restoration that re-captures a snapshot (new timestamp) cannot be recorded as VERIFIED under this contract; a future adapter needs its own explicit comparison policy.
  - Not modelled: a processing graph or ordered effect chain, other operation types, dependency invalidation of derived artifacts, and run-history persistence.
