# ADR-014 — run lifecycle and budget records without a state machine (2026-10-19)
- Status: Proposed; awaiting owner review of the implementing task (Task 2C).
- Decision: extend the dependency-free domain layer (ADR-011 to ADR-013) with `domain.run`.
  1. `RunConfiguration` embeds the fixed run inputs as immutable values (analysis scope, `AnalysisSpec`, `RenderSpec`, `MusicalContext`, `ValidationCriteria`, `ControllerIdentity`, `BudgetLimits`) instead of referencing a mutable configuration file. `validate_against(snapshot)` checks structure only. The run scope and context must reference known tracks. Every condition selector's scope must be known to the snapshot and lie within the run's tracks and time interval. If the run scope restricts frequency, its band may not exceed the render Nyquist frequency, and each condition needs an explicit band inside it. No condition band may exceed the render Nyquist frequency. Comparisons are exact: a band ending exactly at Nyquist is permitted, and frequencies are never clamped. Every condition metric must be listed in the analysis spec. Condition scopes may be subsets of the run scope.
  2. `BudgetLimits` (decision calls, attempts, render calls, recovery operations, elapsed seconds) and `BudgetUsage` (the same quantities) are explicit records with no counters or clock access. Zero count limits are valid; the elapsed limit must be strictly positive. Usage may exceed limits, so that overruns remain recorded evidence; enforcement belongs to the future coordinator.
  3. `Run` records `RunState` (ten working states plus FINISHED, eleven members in total), and on FINISHED a `RunOutcome`, a `FinalProjectState` and a non-blank termination reason. Active records carry none of these. Run outcome and project-output disposition are reported separately. The only combination rule is that SUCCEEDED cannot have UNKNOWN final state. FAILED may leave the project UNCHANGED, and LIMIT_REACHED or CANCELLED may retain accepted edits.
  4. `Run` is a record, not a state machine: no transition methods are defined until attempt and mutation-state contracts exist.
- Source: owner's Task 2C instruction of 2026-10-19; mixing-core design sections 4 (Run) and 6 (lifecycle).
- Rationale: declaring limits, criteria and context before a run (FR-10, QR-04) and recording state, usage and an enumerated stop reason (FR-10, FR-12) need a stable vocabulary. Recording usage rather than rejecting overruns keeps run records honest. Deferring transitions avoids encoding lifecycle rules before mutation and restoration semantics are specified.
- Consequences:
  - Groundwork only for FR-10, FR-12 and QR-04; none is met. Exact rollback (FR-10) will preserve immutable accepted output artifacts and is not modelled here; no approximate restoration is introduced.
  - Not modelled: correction attempts, execution and restoration receipts, run events, monetary or token budgets, gain-movement limits, budget reservations, and Run-to-snapshot consistency (e.g. `initial_revision` versus a snapshot).
  - Whether `FinalProjectState.RESTORED_TO_LAST_ACCEPTED` and `UNCHANGED` can be distinguished reliably depends on the future artifact-based rollback design.
