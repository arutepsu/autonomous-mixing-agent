# Architecture

## Confirmed decisions
- Offline Python processing of synchronized WAV stems; modular monolith with a CLI; no DAW plugin in M0 ([ADR-001](../decisions/0001-offline-python-workflow.md)).
- Deterministic audio analysis and DSP; Claude proposes structured actions but never performs measurements or audio processing ([ADR-001](../decisions/0001-offline-python-workflow.md)).
- Single agent with deterministic orchestration: application code controls the loop, validates proposals, executes DSP and verifies results ([ADR-004](../decisions/0004-single-agent-deterministic-orchestration.md)).
- uv-managed environment, Python 3.11 ([ADR-002](../decisions/0002-uv-dependency-management.md)).
- Track-role-agnostic design: stems carry declared roles; components must not assume specific instruments such as kick/bass. Problem-specific components are added only in their roadmap phase; analysis parameters and thresholds must be configurable and documented ([ADR-006](../decisions/0006-research-first-development-policy.md)).

## Target pipeline (planned)
Audio I/O -> deterministic features -> detectors -> structured problem candidates -> Claude proposal (`decision_agent`) -> action validator -> DSP execution -> verification -> accept/revert -> experiment report.

Hidden-reference boundary ([ADR-010](../decisions/0010-hidden-reference-boundary.md), requirements SR-10): everything up to accept/revert is runtime and never reads the original reference audio or defect-injection ground truth. Run records hold runtime inputs and the action history. Research evaluation joins them with the separately stored hidden evaluation data only after execution.

## Implemented (M0)
M0 implements only Audio I/O -> features -> descriptive JSON report. Do not claim masking detection from overlap measures alone.

| Module | Responsibility |
| --- | --- |
| `autonomous_mixing.audio.io` | Load WAV stems as float64 `(frames, channels)`; reject non-WAV, unreadable, too-short (< 2048 frames), > 2-channel and non-finite input; require equal sample rate and frame count for a pair. |
| `autonomous_mixing.audio.features` | Mono fold-down, RMS/peak dBFS, STFT magnitudes, band-power and temporal-coactivity proxies. |
| `autonomous_mixing.audio.analysis` | `analyze_pair`: combines the above into the `m0.1` report dict, including input SHA-256 hashes. |
| `autonomous_mixing.cli` | `autonomous-mixing analyze`: writes the JSON report; validation errors exit with code 2 and a one-line message. |
| `scripts/generate_test_audio.py` | Deterministic synthetic kick/bass stems, formerly used for manual smoke runs (not perceptual ground truth). No test depends on it; under review per ADR-006. |

Analysis parameters (STFT 2048/512, 30–200 Hz band, 10 % coactivity threshold) are fixed in code. `configs/analysis.yaml` documents them as a proposed manifest but is **not read** by the code yet.

**Known deviations from ADR-006 (M0):** the two inputs are named `kick`/`bass` in the CLI, `analyze_pair` and the report keys, and the parameters above are hardcoded. Retained unchanged until reviewed; do not extend this pattern.

## Domain foundation (implemented records; not integrated)
Proposed in [ADR-011](../decisions/0011-domain-foundation-boundary.md), [ADR-012](../decisions/0012-typed-action-proposals-and-decisions.md), [ADR-013](../decisions/0013-validation-criteria-and-result-records.md), [ADR-014](../decisions/0014-run-lifecycle-and-budget-records.md) and [ADR-015](../decisions/0015-correction-attempt-and-artifact-checkpoint-records.md), [ADR-019](../decisions/0019-fixed-input-gain-and-composite-project-state.md); organized into component packages by [ADR-017](../decisions/0017-domain-component-packages.md). `autonomous_mixing.domain` holds immutable, standard-library-only records with construction-time invariants. Evidence: `tests/unit/test_domain_foundation.py`, which also enforces the import boundary, `tests/unit/test_action_decision.py`, `tests/unit/test_validation_records.py`, `tests/unit/test_run_records.py` `tests/unit/test_execution_records.py`, `tests/unit/test_domain_component_compatibility.py` and `tests/unit/test_domain_component_boundaries.py` (component dependency matrix and public interfaces). M0 does not use these records yet; no requirement is met by them alone.

| Component (`autonomous_mixing.domain.*`) | Files | Public objects (via the component `__init__`) |
| --- | --- | --- |
| `shared` | `identifiers`, `versions`, `invariants` | Opaque IDs (`ProjectId`, `TrackId`, `ArtifactId`, `ObservationId`, `ContextId`, `ActionId`, `DecisionId`, `CriteriaId`, `ConditionId`, `ValidationResultId`, `RunId`, `AttemptId`, `ExecutionId`, `CheckpointId`), `Revision`, `VersionRef`; the `require_*` invariant helpers (finite numbers, counts, UTC timestamps, text, types, tuples, finite derived values) as an intentional input-boundary interface. |
| `project` | `tracks`, `snapshot`, `artifacts`, `checkpoint`, `scope`, `processing`, `state`, `mix`, `processing_spec` | `Track`, `ProjectSnapshot`, `AudioArtifact`, `ArtifactKind` (metadata only; `revision` is the production revision, never retagged; derived end time and Nyquist must be finite), `ArtifactCheckpoint` (artifact membership of one candidate or accepted state; existence is not acceptance), `AnalysisScope`, `TimeRange`, `FrequencyRange`, `TrackGainState` (absolute additional gain relative to a fixed input stem of the track; never a delta on the latest output; absence is never 0 dB), `ProjectProcessingState` (partial coverage allowed), `ProjectState` (snapshot, processing and audio of one candidate or accepted state, consistent by construction; `known_revisions` lists the locally known state and production revisions; a superseded input baseline need not be an audio member). `MixRecipe` and `SummingPolicy` (versioned full-mix recipe: ordered unique logical contributors summed sample-wise without normalization, limiting or clipping; ADR-020), `ProcessingSpec` with `NumericalPrecision`, `GainRule`, `SummationOrder`, `LevelPolicy`, `OutputContainer`, `SampleEncoding` (explicit numerical and encoding configuration: FLOAT64 calculation, `10 ** (gain_db / 20)` on fixed inputs, recipe-sequential summation from zero, no level correction, 64-bit float WAV; ADR-021). |
| `context` | `assertions`, `musical_context` | `AssertionSource`, `TrackRole`, `ContextPreference`, `MusicalContext`; roles are explicit, unknown is absence. |
| `observation` | `observation`, `specifications`, `provenance` | `Observation`, `MeasuredScalar`, `Unavailable`, `AnalysisSpec`, `RenderSpec`, `validate_observation_sources` (sources must be members of an explicit checkpoint matching the snapshot, with identical recorded metadata; production revisions may differ). |
| `action` | `operations`, `proposal`, `execution`, `rollback` | `SetTrackGain` (absolute track gain in dB, no implied bounds), `Action` (proposal vocabulary, not permission to execute), `ExecutionStatus`, `ExecutionIssue`, `ExecutionReceipt` (newly produced candidates plus explicit superseded IDs), `validate_receipt_against_checkpoint`, `derive_candidate_checkpoint` (retained artifacts unchanged, then candidates; does not accept), `validate_gain_execution` (a gain receipt must supersede exactly the target-dependent artifacts and replace them one-for-one by kind and contributor set; metadata only), `derive_candidate_project_state` (runs that check and rejects locally known candidate revisions; complete candidate state: same track inventory and order, only the target gain replaced, inputs unchanged; no rendering or acceptance), `RollbackStatus`, `RollbackReceipt`, `validate_rollback_references`. Rollback selects the complete saved before state (settings, audio and snapshot, exactly), not an inverse transformation; equal metadata is a recorded claim, not proof of exact audio restoration. |
| `decision` | `decision`, `references` | `ControllerIdentity`, `ProposeAction`, `AbstentionReason`, `Abstain`, `Decision` (exactly one outcome), `validate_decision_references` (structural references only). |
| `validation` | `criteria`, `result`, `consistency` | `MetricSelector`, `TargetCondition`, `ImprovementCondition`, `AbsoluteGuard`, `DeltaGuard`, `ValidationCriteria`, `CheckResult`, `ValidationResult` and their enums; `validate_validation_references` (record consistency only). No evaluator, metric formulas or thresholds. |
| `run` | `configuration`, `budgets`, `run`, `attempt`, `references` | `RunConfiguration` (embedded fixed inputs; `validate_against` checks references, scope containment and render Nyquist limits), `BudgetLimits`, `BudgetUsage` (overruns representable), `RunState`, `RunOutcome`, `FinalProjectState`, `Run` (record only, no transition methods), `AttemptDisposition`, `CorrectionAttempt` (complete `before_state`; `candidate_state` required exactly for CANDIDATE_READY execution), `validate_attempt_references` (also requires exactly the requested target gain change). |

**Dependencies between components** (enforced by `tests/unit/test_domain_component_boundaries.py`; acyclic; all may use the standard library and their own internals):

| Component | May import (public interfaces only) |
| --- | --- |
| `shared` | none |
| `project` | `shared` |
| `context`, `observation`, `action` | `shared`, `project` |
| `decision` | `shared`, `project`, `context`, `observation`, `action` |
| `validation` | `shared`, `project`, `observation` |
| `run` | all other components |

Project owns checkpoint membership; action owns deriving candidate membership from an execution receipt, so project stays independent of action. Cross-component and application imports use component interfaces (e.g. `from autonomous_mixing.domain.project import ArtifactCheckpoint`), never another component's internal files. No component imports `run`, and the domain never imports application, infrastructure, M0 audio, presentation or third-party packages.

**Compatibility policy:** the root `autonomous_mixing.domain` exports (all 76 previous names) and the legacy modules `autonomous_mixing.domain.values` and `autonomous_mixing.domain.execution` are thin re-exports of the same objects from their owners, without definitions of their own. They exist for existing callers only; new code and normal tests use component interfaces, and only the compatibility tests import them. Removing them requires a later explicit task. Module-qualified class paths changed and are not a supported persistence format (no pickle compatibility is claimed).

Not yet modelled: problem candidates and uncertainty (FR-05, D11), constraint/preference types (D6), action types and bounds beyond the `SetTrackGain` proposal shape (D5), track kinds/routing/controls, enforcement of protections and bounds, verdict computation and evidence compatibility (evaluator), budget enforcement, lifecycle transitions, dependency invalidation of derived artifacts, artifact I/O, hashing and integrity verification, candidate cleanup, run events and persistence.

## Application contracts (implemented contracts; no services)
Proposed in [ADR-016](../decisions/0016-application-observation-and-decision-contracts.md), [ADR-018](../decisions/0018-explicit-gain-action-admission-policy.md), [ADR-020](../decisions/0020-execution-contracts-and-metadata-preflight.md) and [ADR-021](../decisions/0021-processing-spec.md). `autonomous_mixing.application` depends only on the standard library and the domain component interfaces; the domain never imports it. Evidence: `tests/unit/test_application_contracts.py`, which also enforces both import boundaries, `tests/unit/test_action_admission.py`, `tests/unit/test_execution_preflight.py` and `tests/unit/test_processing_contracts.py`. Nothing in M0 uses these contracts yet, and no requirement is met by them alone.

| Module | Responsibility |
| --- | --- |
| `autonomous_mixing.application.results` | `Success[T]`, `PortFailureCode`, `PortFailure` (code, message, advisory `retryable`), `PortResult = Success[T] \| PortFailure`. |
| `autonomous_mixing.application.contracts` | `AnalysisRequest`/`AnalysisResponse` and `DecisionRequest`/`DecisionResponse`; requests carry one composite `ProjectState` (ADR-019) whose audio membership supplies the sources. `validate_analysis_response` (provenance, spec, metrics, scope containment, completeness, no duplicate metric/scope) and `validate_decision_response` (decision references, controller identity). |
| `autonomous_mixing.application.ports` | `AudioAnalyzer.analyze` and `DecisionController.decide` Protocols returning `PortResult`; `AudioProcessor.process(plan) -> ProcessingOutcome` (no implementation yet). |
| `autonomous_mixing.application.admission` | `TrackGainPermission` (inclusive absolute dB range per track), `ActionAdmissionPolicy` (versioned, per project; empty denies all), `ActionAdmissionRequest`, `AdmissionRejectionCode`, `AdmittedAction`, `RejectedAction`, `admit_action` (fixed order: references, policy project, proposal, protection, explicit permission, bounds; never clamps). An admitted action is a checked proposal, not an execution receipt; the executor must recheck the revision before mutation. |
| `autonomous_mixing.application.execution_contracts` | `StemBinding`, `ExecutionWorkspace` (logical assignment, not a path), `CandidateIdentity`, `ExecutionRequest` (reuses the decision request's single `ProjectState`; carries a required `ProcessingSpec`), `ProcessingPlan` (fixed target input at the requested absolute gain plus already-rendered current stems in recipe order; non-target gains are never applied twice), `ArtifactProcessingEvidence` (adapter claims, including the processing spec used; each output's must equal the plan's as a complete value), `ProcessedCandidate`, `ProcessingFailure` (FAILED or UNCERTAIN only), `validate_processed_candidate` (structural output and evidence checks; lexical location conflicts only). |
| `autonomous_mixing.application.execution_preflight` | `preflight_execution` (pure; first failure wins: rerun admission, workspace, candidate identity, full recipe bindings, selected full mix, explicit target gain state, compatible metadata, no undeclared target-dependent outputs), `MetadataReady`, `PreflightRejected`, `PreflightCode`. `MetadataReady` is not proof of file integrity, alignment, current authorization, workspace safety or exclusive access. |

Not yet defined: analyzers, controllers, the DSP processing adapter and other adapters, file and hash verification, workspace allocation and collision handling, exclusive execution access, the execution service with receipt and candidate-state assembly, orchestration, retries, budget enforcement and render reservations, persistence, CLI integration, and the deferred controller inputs (problem candidates, action capabilities and permitted actions, attempt history, raw provider responses). Admission does not yet cover per-edit or cumulative gain movement, current-gain semantics, adapter capabilities or operation types beyond track gain.

## Open questions
- Open pre-DSP audit findings (2026-10-21; F1 and F5 are corrected, the rest remain open). F2: acceptance evidence is not yet tied to the candidate state; owner: the evaluator/acceptance stage. F3 (narrowed by ADR-021): the processing configuration is now explicit and carried into plans and evidence, but the adapter's subtype mapping, actual evidence and environment provenance remain unimplemented; owner: the DSP and file adapter stage. F4: overwrite protection lacks the complete protected location set and workspace confinement; owner: the file adapter and execution service. F6: potentially misleading names (`AudioArtifact.revision`, `ArtifactCheckpoint`, `FinalProjectState`, `RenderSpec` placement); owner: a later compatibility-planned naming task.
- How should the M0 two-stem interface generalize to role-declared stems (e.g. via the `track_roles` manifest field in [`dataset-plan.md`](../research/dataset-plan.md)), and which report-schema version change does that imply?
- Should `scripts/generate_test_audio.py` be removed or retained (and if retained, for which documented purpose)? Requires owner approval.
- Domain records (ADR-011): how will units be checked against a future metric catalog? Should artifact time coverage allow a tolerance (tied to D3)? Is any zero-offset timezone acceptable as UTC, as currently implemented?
